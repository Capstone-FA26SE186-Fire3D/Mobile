# Unity Android integration (#11–#13, #22)

`unity-artifact.lock.json` is deliberately unpinned until Unity supplies the Android `unityLibrary` export. Fill its `version`, `s3Uri` (`s3://bucket/.../<version>/unityLibrary.zip`) and lowercase archive `sha256` from the handoff. Do not commit credentials or the export. Run `pnpm unity:prepare` with an AWS CLI identity allowed to read that object, then `pnpm android:prebuild`. The script verifies the archive hash before extracting it into ignored `vendor/unityLibrary`; the Expo config plugin verifies that cache and copies it into generated Android during each clean prebuild. Native config requires ARM64 and minSdk 29.

The package verifier follows BE `contracts/package/v1/manifest.schema.json` and Unity `ContentManifest`: `fet3d.package/1`, Android, protocol `1`, a runtime with the app's major version and `minRuntimeVersion` ≤ `2.0.0`, floors by `bundle`, and the manifest SHA-256 pinned by the session. `revisionId`/`materialLibraryVersion` are compared only when BE pins them (playtest pins the revision); `TrainingSessionView` does not, so they come from the hash-verified manifest. The signed URL contract is `GET /api/training/sessions/{id}/package` (and `/api/playtests/{id}/package`) returning `RuntimePackageDownload`; `session-contract.ts` turns it into a plan (HTTPS only, safe unique paths, manifest hash equal to the prepare pin) and cross-checks it against the verified manifest. Downloads go to `<releaseId>/<manifestHash>.partial`, every file is SHA-256 checked, verified files survive cancel/retry, and 403/expired URLs re-fetch the package endpoint. Only a fully verified folder is renamed to `<manifestHash>` and passed to Unity. Online start must return the same session/release/package as prepare, otherwise Mobile stops.

The local Android module implements `com.fet3d.unity.Fire3DUnityBridge.onUnityMessage(String)` and writes each callback (with native receive time) to SQLite before notifying JavaScript. JavaScript (`training-runtime.ts`, mounted for Trainees in `app/_layout.tsx`) subscribes to `onCallback`, copies callbacks to its own SQLite queue before acknowledging native records, confirms `Launched` (valid when Unity reported it before the grant expired, even if confirmed later) and syncs on callbacks, app start and every return to foreground, with 5 s to 5 min backoff. JS timers pause while Unity is in front, so callbacks and AppState drive the loop. `/events:batch` sends at most 500 events, marks accepted/duplicate IDs, retains missing ranges and makes conflicts nonretryable. Completion keeps one idempotency key and treats `AwaitingSync` as pending.

Native lifecycle (assumptions agreed with the Unity side): the first launch in a process waits for `Ready`; when Unity already sent `Ready` and is idle, `Launch` is sent immediately; after `Exited` Unity re-sends `Ready` when back in Bootstrap, and a launch requested meanwhile waits for it (fallback delivery after 5 s). `UnityHostActivity` runs in the app process but in its own task (`singleTask`, own `taskAffinity`, `excludeFromRecents`). On `Exited`, or an `Error` before `Launched` or with `payload.fatal`, Mobile brings the React Native task back **without finishing** the Unity activity: in Unity 6000.6 `UnityPlayerActivity.onDestroy` calls `UnityPlayer.destroy()`, which kills the process (`mProcessKillRequested` defaults to true); `UnityPlayer.quit()` is never called. Back sends `Abort {"reason":"BackButton"}` while a session runs (Unity ends it as Abandoned) and returns to the app when Unity is idle. `onPause`/`onResume` forward `Pause`/`Resume`. "Tiếp tục chơi" calls `show()` to reorder the Unity task to the front.

The integration gate remains open: Unity must supply the export with `Fire3DApp.Resume`, direct `Launch` while idle and `Ready` after `Exited`; Android build, task switching, back handling, repeated sessions and offline sync have not been run on a device. BE must enable live launch; Playwright/TypeScript checks are not Android acceptance.
