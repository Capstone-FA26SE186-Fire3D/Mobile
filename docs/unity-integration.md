# Unity Android integration (#11–#13, #22)

`unity-artifact.lock.json` pins the shared Android `unityLibrary` export by version and archive SHA-256. The current configuration downloads the exact repository/tag/asset under `githubRelease` using GitHub CLI; CI uses its built-in read-only token. See [Google Play release](google-play-release.md) for the one-time asset upload. No AWS configuration is required for this source. Without `githubRelease`, the preparation script supports a versioned S3 URI through `UNITY_ARTIFACT_S3_URI` or `lock.s3Uri` and an AWS CLI identity with read access. Run `pnpm unity:prepare`, then `pnpm android:prebuild`. The archive hash is verified before extraction into ignored `vendor/unityLibrary`; a matching local cache can be reused. A local `--zip` must match the pin too. The config plugin copies the verified runtime into generated Android. Native config requires ARM64 and minSdk 29. The portable export contains precompiled Android libraries and no Windows compiler; Expo can build the Mobile host on Linux. Never commit credentials or the runtime export to Git history.

The package verifier follows BE `contracts/package/v1/manifest.schema.json` and Unity `ContentManifest`: `fet3d.package/1`, Android, protocol `1`, a runtime with the app's major version and `minRuntimeVersion` ≤ the app runtime (`APP_RUNTIME_VERSION`, now `2.0.2`, defined once in `src/features/training/runtime-version.ts` and used for training, playtest and the bridge), floors by `bundle`, and the manifest SHA-256 pinned by the session. `revisionId`/`materialLibraryVersion` are compared only when BE pins them (playtest pins the revision); `TrainingSessionView` does not, so they come from the hash-verified manifest. The signed URL contract is `GET /api/training/sessions/{id}/package` (and `/api/playtests/{id}/package`) returning `RuntimePackageDownload`; `session-contract.ts` turns it into a plan (HTTPS only, safe unique paths, manifest hash equal to the prepare pin) and cross-checks it against the verified manifest. Downloads go to `<releaseId>/<manifestHash>.partial`, every file is SHA-256 checked, verified files survive cancel/retry, and 403/expired URLs re-fetch the package endpoint. Only a fully verified folder is renamed to `<manifestHash>` and passed to Unity. Online start must return the same session/release/package as prepare, otherwise Mobile stops.

The local Android module implements `com.fet3d.unity.Fire3DUnityBridge.onUnityMessage(String)` and writes each callback (with native receive time) to SQLite before notifying JavaScript. JavaScript (`training-runtime.ts`, mounted for Trainees in `app/_layout.tsx`) subscribes to `onCallback`, copies callbacks to its own SQLite queue before acknowledging native records, confirms `Launched` (valid when Unity reported it before the grant expired, even if confirmed later) and syncs on callbacks, app start and every return to foreground, with 5 s to 5 min backoff. JS timers pause while Unity is in front, so callbacks and AppState drive the loop. `/events:batch` sends at most 500 events, marks accepted/duplicate IDs, retains missing ranges and makes conflicts nonretryable. Completion keeps one idempotency key and treats `AwaitingSync` as pending.

Native lifecycle (assumptions agreed with the Unity side): the first launch in a process waits for `Ready`; when Unity already sent `Ready` and is idle, `Launch` is sent immediately; after `Exited` Unity re-sends `Ready` when back in Bootstrap, and a launch requested meanwhile waits for it (fallback delivery after 5 s). `UnityHostActivity` runs in the app process but in its own task (`singleTask`, own `taskAffinity`, `excludeFromRecents`). On `Exited`, or an `Error` before `Launched` or with `payload.fatal`, Mobile brings the React Native task back **without finishing** the Unity activity: in Unity 6000.6 `UnityPlayerActivity.onDestroy` calls `UnityPlayer.destroy()`, which kills the process (`mProcessKillRequested` defaults to true); `UnityPlayer.quit()` is never called. Back sends one `Abort {"reason":"BackButton"}` per launch: while the package is still loading (runtime 2.0.1+) Unity cancels, releases what it loaded and answers `Error LAUNCH_CANCELLED` (never `Launched`), then `Ready`; the training screen shows "Đã hủy mở màn chơi". While a session runs Unity ends it as Abandoned (`Completed`, result screen); Back again on the result screen closes it like its exit button (`Exited`, then `Ready`). When Unity is idle Back returns to the app. After a failed or cancelled launch the bridge treats Unity as idle only on its `Ready` (5 s fallback for runtime 2.0.0, which did not re-send it), and a launch answered `SESSION_BUSY` is kept and delivered on the next `Ready`. Unity's `Ready` carries `runtimeVersion` and `protocolVersion`; the bridge delivers `Launch` (also a queued or retried one) only when both equal the launch payload, otherwise it refuses with `ERR_UNITY_RUNTIME_MISMATCH` or journals `Error RUNTIME_MISMATCH` (fatal) and brings the app back. Before `/start` the app calls `handshake()`: the last `Ready` when Unity already booted, otherwise the runtime the prebuild stamped into the manifest (`com.fet3d.unity.RUNTIME_VERSION`, from the export name `<RuntimeVersion>-<stamp>`; prebuild fails when it differs from `APP_RUNTIME_VERSION`), so a mismatch is reported before Trial or a learner seat is used. BE accepts a session only while that runtime version is an active row of the runtime catalog (Unity `Tools/RuntimeCatalog/README.md`). `onPause`/`onResume` forward `Pause`/`Resume`. "Tiếp tục chơi" calls `show()` to reorder the Unity task to the front.

The integration gate remains open: Unity must supply the export with `Fire3DApp.Resume`, direct `Launch` while idle and `Ready` after `Exited`; Android build, task switching, back handling, repeated sessions and offline sync have not been run on a device. BE must enable live launch; Playwright/TypeScript checks are not Android acceptance.


## Organization playtest (Mobile#22, sections 2–3)

`app/playtest/index.tsx` drives a handed-off playtest with pure rules in `src/features/playtest/playtest-flow.ts` (unit-tested):

- **Prepare** (`Created`/`Launching`, `launchSession`): `GET /api/playtests/{id}/package`, download and verify the manifest and every SHA-256 (`preparePlaytestPackage`), progress, cancel keeps verified files and the next prepare resumes; an already verified package is found again on reopen. Never calls `/start`.
- **Mode**: from the verified `scenario.json` `modePolicy.allowedModes` in runtime order; Guided when allowed, else the first; no policy means every runtime mode.
- **Bắt đầu playtest**: shown only when the package is ready and `launchSession && recovery.canStart`. Runs the handshake, then `/start` with the Idempotency-Key persisted per account + playtest + operation. Double taps are refused while a request runs; a lost response reads the status and replays the same key, so Trial is used once. A replay whose grant expired falls through to `/launch-grants`.
- **Launching**: "Thử mở lại" reissues the grant (`/launch-grants`, persisted key rotated only after that grant expired) and really opens Unity. **Running**: "Quay lại Unity" only while Unity still runs this playtest; gameplay is never restarted automatically. **Completed/Cancelled** are final; replay needs a new playtest from the Web.

Callbacks have one receiver for Trainee training and OrganizationUser playtests (`training-runtime.ts`, started in `_layout.tsx` for both roles), routed by the launch row's `kind`. Every callback is committed to the JS SQLite store before the native journal entry is acknowledged; a callback that breaks the contract is kept as `Rejected`, acknowledged and puts only its session into recovery. Sync runs on each callback, app start and foreground, with backoff. Launch rows carry the starting `account_id` (SQLite migration 2 adds `account_id`, `sync_state`, `recovery_code` with `ALTER TABLE`, keeping pending rows; rows without an account are legacy Trainee sessions) and only the signed-in account's rows are synced. Playtest `Launched` is confirmed with the grant generation; a stale/expired grant, a terminal or foreign playtest, stalled events or `PLAYTEST_EVENTS_INCOMPLETE` with nothing left to resend move the session to recovery (no automatic retry) and stop the play when it is still running. The completion key is stored with Unity's `Completed`, so a lost `/complete` response replays the same key. Relaunching a playtest that BE never saw as launched drops the local events of that attempt.
